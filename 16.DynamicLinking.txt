## Динамическая линковка и динамические библиотеки

В отличие от статической линковки, в которой участвуют объектные модули и результатом которой является исполняемый файл, динамическая линковка происходит в адресном пространстве процесса и не приводит к созданию новых файлов. Она не происходит однократно при сборке приложения, как статическая линковка, а инициируется каждый раз при создании процесса (запуске приложения). В динамической линковке участвуют несколько исполняемых файлов. Как правило, это один основной исполняемый файл приложения и динамические библиотеки. 

# Динамические библиотеки

Динамическая библиотека по сути является разновидностью исполняемого файла, и обычно имеет такой же формат файла, например ELF (Executable Linux File) в Linux или PE (Portable Executable) в Windows. В Windows динамические библиотеки чаще всего имеют расширение .DLL (Dynamic Linking Library), в POSIX-совместимых системах - .so (Shared Object). Как и исполняемые файлы, динамические библиотеки создаются в результате компиляции и статической линковки, но в свойствах проекта или в опциях компилятора необходимо указать что нужно создать динамическую библиотеку.

Динамическая библиотека может быть использована двумя способами:
1. Для динамической линковки, которая происходит автоматически в момент запуска процесса. В Windows любое приложение обязательно использует динамические библиотеки и при запуске любого приложения обязательно происходит динамическая линковка. В Linux при желании можно создавать полностью статические приложения, но обычно так же используются динамические библиотеки.
2. Для динамической подгрузки кода уже в процессе работы приложения, например для того чтобы подгрузить какие-либо расширения или плагины. В Windows вы могли наблюдать это при печати документов - открываются настройки печати для конкретной модели принтера. Для этого подгружается динамическая библиотека, которая поставляется как часть драйвера печати с конкретной моделью принтера. Эта библиотека подгружается именно в тот момент, когда вы открываете свойства печати.

Как устроена динамическая библиотека:
В современных операционных системах исполняемый файл обычно имеет формат состоящий из заголовка и различных секций, этот формат определяется операционной системой. Объектные файлы используемые в статической компиляции и линковке обычно имеют схожую структуру, но конкретный формат файла как правило несколько иной, и может зависеть от используемого компилятора. В заголовке содержится таблица размещения секций (оглавление) и различные параметры, например размер начального стека процесса. Динамическая библиотека это обычный исполняемый файл и отличается только в параметрах, например может не иметь точки входа (entry point) - адреса в кодовом сегменте с которого начинается выполнение процесса.

Обычно исполняемый файл / динамическая библиотека имеют следующие сегменты (название может зависеть от операционной системы):
- Сегмент кода (code или text), в котором содержится код функций реализованных в исполняемом файле или библиотеке
- Сегменты данных (data, rodata) в котором содержатся инициализаторы и различные константные значения
- Таблица экспорта (exports), содержит символы (имена функций/глобальных переменных) которые предоставляет динамическая библиотека и исполняемый файл. Функции обычно задаются как смещения в кодовом сегменте
- Таблица импорта (imports), содержит символы которые используются в коде, но должны быть загружены из другого исполняемого файла / динамической библиотеки
Так же могут содержаться другие сегменты, например ресурсы (иконки, картинки, строки, диалоговые формы) и отладочная информация

# Динамическая линковка в момент запуска программы

Запуск программы начинается с создания контекста процесса и загрузки основного исполняемого файла в адресное пространство процесса. Загрузка файла в современных ОС производится путем отображения файла на адресное пространство через механизм страничного обмена. Для динамической линковки используются таблицы импорта и экспорта основного файла и динамических библиотек. По таблицам импорта происходит загрузка необходимых динамических библиотек и поиск (по их таблицам экспорта) необходимых импортируемых символов. Если динамическая библиотека зависит от других динамических библиотек, то они так же будут загружены, и так пока не будут удовлетворены все зависимости. Если какие-либо символы из таблицы импорта не были найдены - в момент запуска процесса система может выдать соответствующую ошибку. В современных версиях Linux ошибка часто дается только в тот момент, когда происходит обращение к не найденной функции или символу. В Windows обычно требуется полное разрешение всех импортируемых символов до начала работы кода приложения.

Есть многочисленные особенности работы с динамическими библиотеками в различных операционных системах. Например, в Windows в таблице импорта указываются какой символ из какой библиотеки должен быть импортирован, например что функцию CreateProcessW нужно использовать именно из библиотеки kernel32.dll. В Linux имена символов в таблице импорта не привязаны к конкретной библиотеке и отдельно хранится список используемых библиотек.

Как использовать функции из динамических библиотек:
К сожалению, нет какого-либо единого стандарта, использование зависит от языка и операционной системы. Например в Linux обычно не требуется как-либо размечать функции - все функции которые не помечены как статические будут по умолчанию экспортированы, и любая функция которая не была найдена при статической линковке будет помещена в таблицу импорта. 

В Windows необходима специальная разметка:

__declspec( dllexport )

для символов которые необходимо поместить в таблицу экспорта, например

__declspec( dllexport ) double myfunc(double);

Так функция должна быть размечена там, где она реализована.

__declspec( dllimport )


__declspec( dllimport ) double myfunc(double);

Так функция должна быть размечена там, где она используется (в модулях, которые попадут в другой исполняемый файл).
В Windows для того чтобы правильно составить таблицу импорта, помимо dllimport требуется разметить, какая функция (точнее какой символ) в какой динамической библиотеке ожидается. Для этого при статической линковке в проект или в список файлов для линковки надо добавить специальный файл .def (или статическую библиотеку, которая этот файл содержит). def файл / статическая библиотека создаются при сборке динамической библиотеки, и их можно взять оттуда, если динамическую библиотеку вы собираете самостоятельно, однако .def файл это обычный текстовый файл и его можно создать руками, что позволяет использовать произвольные динамические библиотеки. Например

LIBRARY mylib.dll
EXPORTS
    myfunc
    myfunc2

если мы хотим использовать функции myfunc и myfunc2 из mylib.dll. Из .def файла можно создать .lib (библиотеку статической линковки) командой lib, например

lib /DEF:mylib.def /OUT:mylib.lib /MACHINE:x64

Windows позволяет использовать для динамической линковки не только символы (имена функций) но и порядковые номера, указывающие на позицию в таблице экспорта. 

LIBRARY mylib.dll
EXPORTS
    myfunc @1
    myfunc2 @2

Динамическая линковка с использованием порядковых номеров происходит несколько быстрее.

# Загрузка динамических библиотек во время выполнения программы

Динамическая линковка основного приложения происходит в момент запуска программы, однако можно инциировать загрузку произвольной динамической библиотеки в любой момент времени. В Windows для этого используются функции LodalLibrary / GetProcAddress. Например

#include <windows.h>
...
    MODULE hDll;
    double (*myfunc)(double);
    double (*myfunc2)(double);

    hDll = LoadLibrary("mylib.dll")
/* ToDo: проверить hDll не NULL */
    myfunc = GetProcAddress(hDll, "myfunc");
    myfunc2 = GetProcAddress(hDll, "myfunc2");
/* ToDo: проверить myfunc/myfunc2 не NULL */
/* теперь можем использовать функции myfunc/myfunc2 - например передать их в функцию численного интегрирования */

В POSIX-системах используются аналогичные функции dlopen и dlsym.
В случае если библиотека подгружается в процессе выполнения, нет необходимости добавлять ее в таблицу импорта / использовать .def файл.

# Преимущества и недостатки динамических библиотек

Преимущества динамических библиотек:
- Экономия места на диске. Многие приложения используют одни и те же библиотеки, например стандартную библиотеку C или стандартные системные библиотеки. При использовании статических библиотек, код библиотечных функций становится частью кода приложения, и получается что каждое статически слинкованное приложение содержит в себе код одних и тех же функций. При использовании динамических библиотек код функций лежит только в самой динамической библиотеке.
- Экономия памяти. Код статической библиотеки попадает в адресное пространство процесса как часть кода исполняемого файла. Код динамической билиотеки так же попадает в адресное пространство, но как часть кода динамической библиотеки. На первый взгляд это не приводит к экономии памяти, т.к. в обоих случаях нужна память для отображения кода. Однако, в современных операционных системах загрузка динамической библиотеки происходит через механизм страничного обмена (путем отображения файла динамической библиотеки в адресное пространство процесса). Большая часть страниц памяти с кодом отображены в адресное пространство в режиме только на чтение (read only). Поскольку страницы с кодом в разных процессах отображены на один и тот же файл динамической библиотеки, операционная система будет использовать в физической памяти одни и те же страницы, отображая их в адресные пространства различных процессов относящихся к разным приложениям. Т.е. например если два разных процесса двух разных приложений prog1.exe и prog2.exe используют общую динамическую библиотеку lib1.dll - в физических страницах памяти будет находиться только один экземпляр кода, который будет отображен в адресные пространства различных процессов. Для статических библиотек такой экономии не будет, потому что код находится в разных исполняемых файлах и операционная система не знает что это одни и те же данные.
- Удобство обновления. Например, если в библиотечной функции обнаружена ошибка - в случае динамической библиотеки достаточно обновить только саму динамическую библиотеку. В случае статической библиотеки необходимо заново собрать и обновить все приложения, которые используют проблемную функцию.
- Возможность абстрагирования системных вызовов или других низкоуровневых объектов. Например, в Windows код основного приложения никогда не выполняет системные вызовы напрямую. Вместо этого используются функции Windows API которые реализованы в динамических библиотеках (kernel32.dll, user32.dll, gdi32.dll и других). Это позволяет одной и той же сборке приложения (одному и тому же исполняемому файлу) работать в разных версиях Windows, несмотря на то что системные вызовы в них реализованы по-разному.
- Возможность расширения функциональности приложения. Например, сторонние разработчики могут разрабатывать  расширения (плагины) для графического редактора (Photoshop, GIMP и тп) - такие расширения обычно реализуются как динамические библиотеки.

Недостатки динамических библиотек:
- Вызов функции статической библиотеки происходит за одну операцию, обычно машинной инструкцией CALL со смещением относительно текущего адреса. При динамической линковке, адреса функций обычно заносятся в таблицу (IAT - import address table или GOT - global offsets table) и вызов функции происходит опосредованно - из известной позиции в таблице берется абсолютный адрес функции и уже по нему происходит вызов. Это может требовать одну более сложную инструкцию или несколько инструкций, в зависимости от архитектуры, что медленней, хотя разница не значительна. Однако, в случаях когда компилятор на этапе компиляции не знает, что вызов надо производить опосредованно, необходима статически линкуемая функция, которая будет производить поиск нужного адреса, такая функция генерируется в процессе линковки. Тогда вызов происходит в несколько этапов - сначала вызывается локальная функция, а уже из нее ищется адрес функции динамической библиотеки и проивзодится вызов функции динамической библиотеки. Это уже достаточно накладно. Конкретная ситуация зависит от архитектуры, компилятора, параметров компиляции и линковки и наличия специальной разметки в описаниях функций, которая подсказывает компилятору как именно надо производить ее вызов.
- Преимущства динамических библиотек обычно достигаются только в том случае, когда все приложения используют один и тот же экземпляр библиотеки. Для этого библиотека должна располагаться в общей системной директории, что требует повышенных привилегий для установки программы.
- В экосистеме Windows преобладает ПО с закрытым кодом. В ПО с закрытым кодом как правило используются собственные библиотеки, кроме системных и стандартных библиотек из-за особенностей лицензирования, что нивелирует преимущества динамических библиотек.
- В экосистеме ПО с открытым кодом, например Linux из-за отсутствия единых стандартов и излишего экспорта символов (все нестатические символы экспортируются по умолчанию и не привязаны к библиотеке при динамической линковке), случаются коллизии символов между разными проектами.


# А что в python?

Python это интерпретируемый язык, и как таковых динамических библиотек и процесса динамической линковки при запуске программы в нем нет, и на python невозможно написать динамическую библиотеку (по крайней мере в ее обычном понимании), однако можно использовать динамические библиотеки написанные на C (или других языках) с помощью библиотеки ctypes. Таким образом можно использовать загрузку динамических библиотек во время выполнения программы.
